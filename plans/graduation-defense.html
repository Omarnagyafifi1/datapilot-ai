The Problem

🔒

Data Locked in Databases

Organizations store critical data in relational databases, but accessing it requires SQL expertise — a skill most business users, analysts, and decision-makers don't have.

⏱️

Slow Bottleneck

Every data request creates a dependency on specialized engineers. A simple question like "What was our total revenue last quarter?" waits in a queue for hours or days.

🌐

Language Barrier

Most Text-to-SQL systems support English only. Arabic-speaking users — a massive market — are underserved by existing solutions.

⚠️

Data Safety & Trust

Blindly executing AI-generated SQL is dangerous. Systems need safety guards — write-protection, human approval loops, and robust error recovery — that many existing tools lack.

Let me start by framing the problem. Data is the lifeblood of modern organizations, but it's locked inside databases that require SQL — a language spoken by maybe 5% of employees. Business users have to file tickets, wait for engineers, and reformat their questions multiple times. For Arabic speakers, the problem is even worse — most Text-to-SQL systems are English-only. And even when AI generates SQL, doing it safely — preventing accidental data loss — is a serious engineering challenge. DataPilot AI addresses all three: the language barrier, the expertise gap, and safety.

🔑 Key Design Decisions

  • StateGraph — 14 typed nodes with conditional edges
  • Intent Router — Regex heuristics first (fast), LLM fallback for ambiguity
  • Schema Filtering — LLM prunes schemas >10 tables to save tokens & improve accuracy
  • Scenario Memory — FAISS-powered similarity search against past queries (threshold: 0.45)
  • Auto-Retry — Up to 3 fix-attempt cycles with progressive error context
  • HITL Approval — LangGraph interrupt() with configurable TTL
  • Parallel Post-Process — Viz + Insights + Suggestions run concurrently via ThreadPoolExecutor

This is the heart of the system — the LangGraph agent. Let me walk through the flow. When a question arrives, the Router classifies it into one of four intents: INQUIRE (read), ADD, DELETE, or UPDATE. It uses regex heuristics first for speed — checking for interrogative words, Arabic question patterns — and only falls back to the LLM for ambiguous cases. Next, we fetch the database schema. If the schema has more than 10 tables, we use a second LLM call to filter it down to only the relevant tables and columns — this dramatically reduces token usage and improves SQL accuracy. Then we load long-term memory from the LangGraph Store — past successful queries for this database. If we have a scenario memory with FAISS — a vector similarity search against past resolved queries — we may reuse a previous SQL directly, skipping LLM generation. For write operations, the flow hits an approval node that uses LangGraph's interrupt mechanism to pause execution and wait for human confirmation via the UI. The SQL execution node has a safety check blacklisting dangerous keywords like DROP, ALTER, TRUNCATE. If execution fails, the fix-sql node sends the error message back to the LLM with context to generate a corrected query, up to 3 retries. After success, we run visualization, insight, and suggestion generation in parallel using ThreadPoolExecutor. Finally, we document and persist to long-term memory.

One of the most architecturally important decisions was the LLM Factory with automatic failover. Instead of hard-coding a single provider, we defined a BaseLLM abstract class and implemented six concrete providers. The Azure OpenAI provider supports two modes: the standard Azure OpenAI SDK for dedicated deployments, and the AI Foundry serverless API — both handled transparently. The critical piece is the FallbackLLM wrapper. This gives us effectively 99.9%+ uptime for LLM generation. The entire provider configuration is runtime-mutable — users can change their preferred model from the Settings panel and the orchestrator resets on the next request.

📝 Prompt Architecture

  • SQL_GENERATION_PROMPT — 28 rules including bilingual support, column mapping, join strategies, strict schema matching
  • SQL_FIX_PROMPT — Debugging prompt with failed SQL + error + schema + scenario context
  • SQL_ADD/UPDATE/DELETE_PROMPT — Specialized for write ops with safety mandates
  • INSIGHT_PROMPT — Generates 3-5 bilingual insights as structured JSON
  • SUGGESTION_PROMPT — Generates bilingual follow-up questions
  • INITIAL_SUGGESTION_PROMPT — Schema-based starter questions for new connections
  • CONTEXT_FILTER_PROMPT — Schema pruning for large databases
  • INTENT_ROUTER_PROMPT — Fallback intent classification
  • SCENARIO_LESSON_PROMPT — Structured 4-section lesson generation

📏 Key Prompt Rules

  • Rule 5: NEVER use SELECT * — only requested columns
  • Rule 8: Top-N queries → ORDER BY + LIMIT (not DISTINCT)
  • Rule 11: HAVING for aggregate filters, include agg in SELECT
  • Rule 14: "Per X" queries → JOIN to get the name, never ID alone
  • Rule 21: Data not in schema → output SELECT 'ERROR: ...' AS error
  • Rule 22: Full Arabic pipeline with 5-step translation process
  • Rule 28: Fuzzy table matching as last resort before ERROR

A key differentiator of DataPilot AI is its bilingual support. Arabic questions follow a rigorous 5-step pipeline encoded directly into the prompt: detect Arabic Unicode characters, mentally translate to English, map to actual English column names in the schema, identify the SQL technique, and generate SQL using only English identifiers. The prompt has 28 carefully crafted rules — covering everything from Arabic keyword mappings like "إجمالي" → SUM, to join strategies, to strict schema matching. If the schema doesn't contain the requested data, Rule 21 forces the LLM to output an explicit error rather than guessing. We also have specialized prompts for write operations that mandate WHERE clauses to prevent accidental mass updates. The insight and suggestion prompts generate structured JSON output — bilingual, with both Arabic and English fields — that the frontend renders side by side.

Scenario Memory — Continuous Learning

🧠 FAISS-Powered Memory

class ScenarioMemory:
    def __init__(self, path, threshold=0.45):
        self.path = path  # scenarios.md
        self.threshold = threshold
        self._faiss_index = None

    def _embed(self, text: str, dim: int = 512):
        vec = np.zeros(dim, dtype=np.float32)
        for token in self._tokenize(text):
            digest = hashlib.md5(
                token.encode()).digest()
            idx = int.from_bytes(
                digest[:4], "little") % dim
            vec[idx] += 1.0
        # L2-normalize for cosine similarity
        return vec / (np.linalg.norm(vec) or 1)

    def find_similar_solution(self, question):
        entries = [e for e in self._load()
                   if e.status == "resolved"]
        vectors = np.vstack([self._embed(e.question)
                             for e in entries])
        query = self._embed(question).reshape(1, -1)
        index = faiss.IndexFlatIP(vectors.shape[1])
        index.add(vectors)
        scores, idxs = index.search(query, 1)
        if scores[0][0] >= self.threshold:
            return entries[idxs[0][0]].sql
        return None

♻️ Learning Loop

  • Success → Stored with SQL + question for future reuse
  • Failure → LLM generates a structured 4-section lesson
  • Lessons injected into fix and generation prompts as scenario_context
  • FAISS threshold 0.45 enables fuzzy matching of similar questions

One of the most innovative features is the Scenario Memory — a continuous learning loop that makes the agent smarter over time. Every query — successful or failed — is stored in a scenarios.md file with structured metadata. For failures, the LLM generates a full 4-section lesson: what went wrong, the correct approach, the correct SQL, and a key takeaway. These lessons are injected into the prompt context for future queries, so the agent literally learns from its mistakes. For success cases, we use FAISS to embed the question along with its SQL. When a new question arrives, we compute its hash-based embedding and search for similar resolved queries. If the similarity score exceeds 0.45, we reuse that SQL directly — skipping the LLM generation entirely. This gives us faster response times for repeated query patterns and a growing knowledge base.

🛡️ Safety Layers

  • 🔴 Hard block: DROP, ALTER, TRUNCATE, GRANT, REVOKE, EXEC

Quality assurance runs at multiple levels. Every SQL goes through syntax validation (forbidden keywords, SELECT/WITH only, has FROM, balanced parens), then multi-dimensional LLM evaluation with a weighted overall score. After every query, we post structured feedback to LangSmith for tracked metrics over time. Three SQL safety layers: hard block on dangerous operations, write-approval for modifications, and retry limits to prevent infinite error loops.

Security Architecture

🔐 Credential Encryption

  • Database passwords encrypted with Fernet (AES-128-CBC + HMAC-SHA256)
  • LLM API keys stored encrypted in settings.json
  • Encryption key from ENCRYPTION_KEY env var (never in code)
  • Decrypted only at query time, never cached in plaintext

🛡️ SQL Injection Prevention

  • Layer 1: LLM prompt instructs against dangerous SQL
  • Layer 2: Generation node validates output against keyword blacklist
  • Layer 3: Execution gateway re-validates before running
  • Layer 4: HITL approval for all write operations

🔒 API Security

  • CORS restricted to FRONTEND_URL in production
  • Rate limiting: 120 req/min per client
  • Request ID tracing via X-Request-ID headers
  • Health check for Azure Container App probes

Security was designed as a layered defense. At the credential layer, all passwords are encrypted with Fernet using an environment variable key, never hardcoded. At the SQL injection layer, we have four defenses: the LLM prompt, generation node validation, execution gateway re-validation, and human approval for writes. At the API layer, we have CORS restrictions, rate limiting at 120 req/min, request ID tracing for audit trails, and no sensitive data leakage in error responses.

Engineering Challenges & Solutions

⚠️ Schema Hallucination

Problem: LLMs invent table/column names when schemas are large or ambiguous.

Solution: 2-stage pipeline — fetch real schema via SQLAlchemy Inspector, then LLM-filter to relevant tables. Rule 21 forces ERROR if data not in schema.

⚠️ SQLite Path Migration

Problem: SQLite paths in DB break when container restarts or directory changes.

Solution: Path resolution searches 11 locations, auto-backup/restore via Azure Files, in-memory path migration at startup.

⚠️ LLM JSON Parsing

Problem: LLMs inconsistently wrap JSON in markdown, use single quotes, or add trailing commas.

Solution: 4-strategy parser: markdown extraction → brace matching → quote fixing → direct parse with graceful fallback.

⚠️ Provider Rate Limits

Problem: Free-tier providers (Groq, Gemini) have strict rate limits causing 429 errors.

Solution: FallbackLLM wrapper with priority-ordered failover. Suggestion caching eliminates redundant calls.

⚠️ CORS Preflight

Problem: Browsers send OPTIONS preflight that wasn't handled.

Solution: Custom middleware with explicit OPTIONS handler and catch-all route. Works across dev localhost and production domain.

⚠️ Oracle System Noise

Problem: Oracle's system tables (LOGMNR$, MVIEW$) polluted schema context.

Solution: System table filters for Oracle (20+ patterns) and MSSQL. 50%+ reduction in schema noise for enterprise DBs.

We faced six major engineering challenges. Schema hallucination — solved with a 2-stage real-schema-then-filter pipeline. SQLite path management — solved with 11-location path resolution and automatic Azure Files backup/restore. LLM JSON parsing — solved with a robust 4-strategy parser. Provider rate limits — solved with FallbackLLM chaining and caching. CORS preflight — solved with custom middleware. Oracle system table noise — solved with dedicated filtering. Each challenge resulted in a reusable solution that made the system more robust.
