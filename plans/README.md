## Findings considered and rejected

- **SQL injection via /query endpoint `sql` field bypasses safety** (SEC-02): The `sql` field in `QueryRequest` is used by the frontend pagination flow to pass the generated SQL to the graph. Blocking it would break the legitimate flow. The SELECT-only validation added in plan 024 addresses the risk. Not a separate plan.
- **Session-based auth missing** (SEC-07): Adding auth retroactively is a product decision that depends on deployment topology (VPN-protected vs. public). Not actionable without product direction. Flagged for the maintainer's awareness.
- **SSRF via datasource connect** (SEC-11): Internal network scanning is possible but mitigating it (blocking private IPs) is a hardening step that depends on deployment network topology. Not a plan without deployment context.
- **Weak static encryption key** (SEC-05): The current Fernet encryption works correctly for development. KMS integration is a production concern, out of scope for this audit. Flagged for awareness.
- **Plan 001 code already deployed**: `graph.py:723-729` already invalidates `_STALE_CACHE` and `_SCHEMA_CACHE` on writes. Plan 001 is correctly marked DONE.
- **Plans 020, 021 marked DONE**: Both plans were implemented in earlier sessions. Code verified: FK metadata in schema, `max_tokens=1024` in sql_node, combined router+filter node, semantic caching, eval sampling at 20%, and all other 020/021 changes are live in commit 0d59108.
